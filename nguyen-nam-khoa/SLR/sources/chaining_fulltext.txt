ABSTRACT Software testing is a crucial activity in the software development cycle, as it verifies
code correctness, reliability, and maintainabilily. Unit testing involves verifying the correctness of the
individual components of a program. Manually writing these tests is resource-intensive and time-consuming.
Researchers have proposed various automated test generation methods to overcome this problem. Large
Language Models have shown great success in automatically generating unit tests recently. Although a single
LLM configuration can produce satisfactory responses, there are possible risks to the effectiveness of the
generated tests. We present a novel method, LLM Chaining, that uses the collaboration of several LLMs,
namely Gemini, GPT-4o, and Claude-3.5 Sonnet, to collaborate and iteratively enhance tests. We began
by testing a single LLM writing unit tests, but after noting their suboptimal performance, we explored LLM
chaining as a method to enhance the accuracy and coverage of the produced tests. Gemini and GPT-4o yielded
the most reliable results of all the configurations we tested. Under this configuration, the LLM system uses
Gemini to generate the initial JUnit tests, then sends the generated results to GPT-4o to improve accuracy.
The HumanEval dataset was used to create JUnit test cases for this study. JaCoCo is used to collect coverage
statistics, and PIT is used for mutation-based testing to measure an LLM’s ability to detect faults in tests.
Our approach achieved 99.05% branch coverage, 90.48% line coverage, and 94.32% mutation coverage.
In contrast, Randoop, a well-known automated test generation tool, obtained 68.64% branch coverage and
78.84% line coverage. This demonstrates how multi-step LLM refinement works well to advance automated
test generation.

I. INTRODUCTION
Software engineering is a specified and measurable process
for designing, implementing, and maintaining software [1].
It serves as a process to ensure that the software is reliable,
works as intended, and meets user desires. In software
engineering, one activity is more important than others—
software testing, which is the process by which we check

behaves as rationally intended [2]. Software testing is a
formal assessment of a system, or an element of a system,
to identify defects, find nonconformity with requirements,
and assert anticipated behavior. Testing is a vital phase of
the software development life cycle since it contributes to
minimizing defects in production software by verifying the
software prior to deployment into production [3].
Unit testing is the lowest level of software testing. It aims
to ensure that individual functions or units are correct.

Developers normally write test cases automatically before
writing the functionality to ensure that each unit is as
required. In a standard unit testing cycle, tests are run; if
they succeed, then the functionality either is right or already
exists. If a test fails, the developer makes changes to the code
and repeats the tests until they succeed. After passing the
tests, project stakeholders are able to inspect the results in
terms of feedback. This is a process that is especially valuable
and practical for medium- to large-sized projects [4]. Unit
tests minimize the risk of releasing faulty software, make
debugging easier, and allow early bug detection[5]. They also
improve the software and reduce maintenance cost in the long
run.
Manual unit testing is time-consuming and involves a
high degree of error. Test cases are produced by developers,
tests are executed, and output is inspected through the
console—which is not very scalable for systems that are
not trivial. In addition, the time it consumes to test manu-
ally is more and significantly raises software construction
cost [6].Researchers have investigated automation as a means
of enhancing test coverage and efficiency.
Standard automated testing techniques, such as symbolic
execution, evolutionary algorithms, and model checking,
have been developed through extensive path exploration
within a program. However, such conventional techniques
might not reflect the underlying intent of the code
and hence restrict their applicability in comparison to
human-generated tests [7]. They continue to struggle with
generating high-quality test cases that accurately capture
real-world applications even though they assist in widening
coverage.
Automated test generation is addressing some of the
problems associated with manual testing by saving time and
improving scalability. Secondly, sites like GitHub and Stack
Overflow have transformed testing in the way we are now
able to share our tools, our expertise, and our methods to
the entire globe [8]. These sites facilitate quicker iteration
and more automation in test generation, leading to reduced
development time and improved software quality.
Researchers are beginning to use machine learning (ML)
and deep learning (DL) technologies to generate tests as
a reaction to the issues caused by modern-day software
complexity. These technologies use learning from code to
develop better tests. As DL-based technologies improve
coverage, these approaches do have some limitations: they
struggle with scalability and they don’t have enough training
data. These limitations prevent them from understanding code
intent fully and designing the best test cases possible [9].
The emergence of Large Language Models (LLMs)—
such as OpenAI’s GPT-3 and Codex—has been a major
boost to software testing. LLMs are extremely good at
understanding codes and doing tasks in natural language,
making them perfect candidates for automatically writing
unit tests. Additionally, LLMs can rewrite tests when given
feedback about errors, making the tests more trustworthy.
This technology is encouraged by open platforms such as
GitHub that support creativity and encourage community
gains and improvements [8].
Regardless of this development, the LLM-based approaches
still present substantial challenges. Single-pass generation
with static prompts often creates test cases that either
will not compile, have no meaningful coverage or provide
poor practices [10]. Although quick engineering is widely
used, manual testing cannot be completely replaced by it.
Issues with privacy, explainability, and security continue to
exist [12]. Current approaches are deficient in providing the
iterative improvement and collaborative thinking necessary
to produce complete and trustworthy tests.
We introduce an approach designed to fill the gaps in
automated unit test generation under the name of LLM
Chaining. LLM Chaining allows multiple large language
models (LLMs) to collaborate in a structured and iterative
way so that test cases can be generated in high quality,
and now the high quality is not based just on single-step
generation, but each of the strengths of the different models
like Gemini, GPT-4o, Claude-3.5 Sonnet, etc.
The key contributions of this research are:
• We perform a comprehensive coverage analysis using
both single LLM and LLM chaining approaches,
evaluating their effectiveness through line and branch
coverage metrics.
• We perform mutation testing to assess the fault-detection
capability and robustness of LLM-generated test cases
compared to refined LLM chaining methods.
• We compare LLM-generated test cases with the non-
LLM (Randoop) baseline to demonstrate the relative
performance of AI-driven versus conventional auto-
mated test generation methods in terms of coverage.
We evaluated this technique using the HumanEval dataset
and measured coverage metrics with JaCoCo. Our automated
pipeline ran 3,508 test cases, recording 99.05% branch
coverage, 90.48% line coverage, and 94.32% mutation
coverage, including regions of previously unexplored code.
These findings illustrate that LLM Chaining has the potential
to greatly enhance automated unit test generation, resulting
in stronger and more maintainable software.
II. BACKGROUND AND RELATED WORK
A. THE SIGNIFICANCE OF SOFTWARE TESTING
In the software development life cycle, software testing is
a crucial step that guarantees systems meet user needs and
adhere to industry standards. Testing is common to measure
system functionality, reliability, security, and performance
under various scenarios as systems grow larger and more
complex, particularly with features like microservices. Early
detection of defects reduces repair costs and prevents system
failures [13]. More recently, advancements in high-quality
Large Language Models (LLMs) have addressed the present
constraints of assessing intricate, real-world applications,
opening up exciting opportunities for test generation automa-
tion [14].

While performance testing ensures that a software program
remains responsive when user demand increases, security
testing protects sensitive data from security incidents. Regres-

affect software. When combined, these testing methods lower

despite its importance. With all of the microservices and

testing result from this. Advances in AI and LLMs, like

tests, which have improved test success and increased cov-
erage [16]. However, current AI techniques frequently result
in tests that are either inadequate or poorly contextualized,
highlighting the necessity for sophisticated strategies to
handle system complexity.
B. UNIT TEST GENERATION
Automated unit testing is turning out to be a cost-effective
way to improve software quality and decrease manual
testing burden. The landmark in this regard is the research
paper of Fraser and Arcuri [17] entitled ‘‘Whole Test Suite
Generation.’’ They used the EvoSuite tool for introducing
search-based software testing (SBST) for Java. EvoSuite
significantly boosted test coverage and fault detection, paving
the way for tools like EvoMaster [17]. The integration of
SBST (Search-Based Software Testing) in Web API testing
has paved the way for new research directions. Despite
the development of more advanced methods, SBST remains
effective in generating well-structured and practical test
cases. Modern tools apply various techniques, such as random
data generation, feedback-directed testing, and combinatorial
testing, to create JUnit tests for software developed in
different programming paradigms.
Advanced techniques like symbolic execution and concolic
testing have also increased the space of test generation that
is possible for applications of C and Java. Constraint-based
reasoning has also had its share of influence, particularly
in the generation of tests for programs from Java bytecode.
These methods, however, are confronted with challenges
in representing complex constraints, interaction with SQL,
and support for dynamic programming languages. Also, they
are generally rigid to fit runtime environments or specific
research inputs. To address these shortcomings, dynamic and
adaptable frameworks have been established. These types
of frameworks generate low-error, coherent test cases by
addressing Java bytecode and opcode directly, leading to
more reliable unit testing approaches [18].
Despite these advancements, scalability is a significant
concern. Symbolic execution may be plagued by path
explosions in complex systems, yet genetic algorithms, while
beneficial, are computationally costly, as noted by Fraser and
Arcuri [19]. Other methods employ UML sequence diagrams
to specify component interaction in order to obtain unit tests
that verify functional and non-functional requirements, e.g.,
error handling in dynamic systems [20].Systematic reviews
indicate that quality is guaranteed with assurance of reduced
manual effort with automated tools. Automated tooling, how-
ever, suffers from the absence of common evaluation criteria,
rendering findings generalizable across tools problematic.
V ariation in tool capability for dealing with functionality,
scalability, and integrability further complicates the picture.
Recent surveys mitigate these issues by focusing on
tools that have feedback mechanisms and systematic test
generation techniques, and they provide a direction towards
future research [21]. Unit testing has also become extremely
important in fields like reinforcement learning, where the
reliability of algorithms is of the highest priority. For instance,
one of the most popular Python packages for reinforcement
learning had 95% code coverage through automated tests,
which were themselves tested against reference implemen-
tations. Reproducible research was also stressed, enabled by
stable interfaces and quality documentation [22]. Although
these methods work well in most situations, they typically
depend on pre-curated datasets, limiting their applicability to
other codebases. Advances such as iterative LLM-based test
generation are more flexible and scalable, thus overcoming
these previous limitations.
C. LARGE LANGUAGE MODELS FOR UNIT TEST
GENERATION
Large Language Models (LLMs) have introduced a new era
for automated coding tasks, such as unit test generation,
by being able to produce syntactically correct code and test
cases. Chen et al. [23] provided early evidence of what
LLMs could do when they produced JUnit-like test cases
from natural language specifications or code snippets with
Codex. The test cases provided by Codex were syntactically
correct tests in [23]. Later work by Liu et al. [24] leveraged
GPT-3.5 and was able to generate well-formed unit tests,
especially in simpler contexts, but ran into test completeness
and coverage issues.
More recent breakthroughs with models like GPT-4 have
enhanced executable test generation [24]. Nonetheless, even
GPT-4 suffers from issues caused by single-pass inference
and limits to prompting styles, resulting in bugs such
as incomplete edge case coverage, redundant assertions,
and common anti-patterns in test structure [24]. These
constraints, such as not being able to iteratively improve
tests or take advantage of collaborative reasoning between
models, encourage further sophisticated methods. Compiling
a direct comparison of the efficacy of different LLMs, Patel
et al. [25] discovered that Gemini is better suited to writing
code, whereas Claude-3.5 Sonnet is better at detecting errors
in code-generation attempts [24]. Together, these works

underscore the ability of LLMs to lower manual testing

To classify test generation using LLMs, we present the
following taxonomy:
• One-shot LLMs: Produce tests in a single inference
step with static prompts, as in early applications of
Codex [23]. These are efficient but tend to be incomplete
and context-insensitive.
• Feedback-tuned LLMs: Use feedback loops to iterate
towards test case improvement, as investigated with
GPT-3.5. These better maintain quality but are still
bound by single-model limitations.
• LLM Chaining: A multi-model, iterative approach
in which several LLMs (e.g., Gemini and GPT-4o)
jointly construct and iteratively improve tests, increasing
correctness and coverage.
The progress of testing with large language models
(LLMs) indicates that an ‘‘LLM Chaining’’ approach may
form an iterative procedure using several LLMs. In this
method, later models (like Gemini and GPT-4o) start from
the output of earlier models in the pipeline and hence
potentially improve on correctness and test coverage. This
iterative and multi-model process may break away from
conventional single-model and single-inference techniques
and provide a new model for creating tests innovatively and
iteratively in different software settings. By addressing the
long-standing limitations of even sophisticated models such
as GPT-4—such as incomplete coverage and prevalent anti-
patterns—LLM Chaining offers a more solid and dependable
approach to automatic unit test generation. Table 1 compares

D. LIMITATIONS OF CURRENT APPROACHES IN APPL YING
LLMS TO UNIT TEST GENERATION
Although LLM-based tools are very promising, there are
several key limitations that need to be resolved. Most
significant among these is generating non-compiling or
semantically incorrect tests. According to a report in [30],
30% of tests generated by Codex did not compile due to
problems such as missing imports, incorrect use of APIs,
undefined variables, or mismatching signatures. Even if
compilation passes, semantic bugs—such as wrong assertions
or miscalculated logic—can provide a wrong impression of
correctness.
Another significant limitation is lack of code coverage. For
example, Fang et al. observed GPT-3 only covered 60% of
branches in complex code, given to often neglect edge cases
important for robustness [31]. Flawed practices—like redun-
dant assertions or weak validation (e.g., assertTrue(true) or
assertNotNull(result) without context)—also decrease test
suite quality, as Kang et al. discussed [32].
Additionally, single-pass, static prompt-driven generation
limits flexibility across various codebases and changing
needs—a problem noted by Zhang et al. [33]. While
partial remedies such as prompt engineering [34], [35] and
post-processing regulations [32] exist, they tend to be ad hoc
and incoherent.
These limitations bring ethical and security issues. Pass-
ing tests incorrectly can deceive developers, particularly
in safety-critical use cases. Flawed tests included within
CI/CD pipelines under lax control may cause production
problems of a serious nature. The code generated could also
accidentally include insecure patterns or break compliance
standards, particularly in use cases with sensitive or regulated
data.
To address those requirements, we introduce our LLM
Chaining architecture—a multi-LLM sequential pipeline for
improved syntactic and semantic correctness. In this pipeline,
Gemini produces the first test, while GPT-4o refines and
checks that test. This layered structure ensures improved
alignment with an evolving codebase and results in higher-
quality tests. Initial empirical findings on the HumanEval
benchmark determined that LLM chaining obtains 99.05%
branch coverage and 90.48% line coverage, which is better
than single-model methods. This iterative improvement
enables LLM chaining to adaptively cope with modular
code modifications, effectively represent developer intent,
and serve as an extensible and reliable approach to unit test
automation.
III. METHODOLOGY
This section explains how large language models (LLMs) are
used to automatically create Java test cases from start to end.
The process focuses on using the complementary strengths of
LLMs to automatically create high-quality test suites that use
JUnit to test Java programs.
The Figure 1 shows the architecture diagram of the multi-
stage pipeline, which shows how the proposed system will
work as a whole.
The process consists of five main steps that work together
to improve the quality and coverage of the test cases that
are made while also making it easier to do the work by
hand. These stages include: (1) Source Code Analysis, (2)
Test Case Generation using Gemini, (3) Test Refinement
using GPT-4o, (4) Final Test V alidation, and (5) Coverage
Measurement.
A. SOURCE CODE ANAL YSIS
This stage focuses on extracting meaningful structural and
semantic information from Java source code to guide
effective test generation. It combines the use of a benchmark
dataset with a parsing mechanism to identify and interpret
code elements that influence how LLM prompts are con-
structed and test cases are generated. The subsections below
describe the dataset used and the specific process of code
analysis.

B. TEST CASE GENERATION USING GEMINI API
Gemini is instructed to generate an comprehensive JUnit test
class. Because of Gemini’s exceptional ability to produce
lengthy, cohesive, and structurally sound code completions—
particularly for Java test cases—we chose it as the first test
generator. Creating lengthy, multi-method JUnit test classes
from the raw source code metadata was a good fit for
Gemini. Gemini’s high token efficiency and ability to follow
instructions were valued by us. At this point in the pipeline,
its ability to efficiently generate correctly formatted code in
a single pass is essential to maintaining the output’s syntactic
and semantic integrity and avoiding premature truncation.
Using the structural metadata from the previous step, this
step generates a prompt asking the Gemini model to produce
particular, syntactically correct test classes. We started with
very basic instructions like ‘‘generate JUnit test cases,’’ but
we ran into problems with incomplete code, skipped edge
cases, and private methods that shouldn’t have been tested.
In order to address this, we began adding more information
to the prompts, like method names, the quantity of conditions,
and data types, which improved the model’s comprehension
of the code. The main goal is to use applicable and realistic
inputs to exercise all of the executable lines and conditional
branches. The generated test code must not contain private
methods, adhere to JUnit standards, and work with the
original Java class. The following should be the prompt
strategy:
• Use complete Java source code within triple backticks
for syntax readability.
• State the exact number of branches (estimated from if
and switch statements).
• State all data types used in the class that are relevant (int,
boolean, String, etc.).
• Tell the model to generate test cases for all paths of
execution, edge cases (zero, negative, and boundary
values), and invalid input scenarios.
• Demand significant assertions and good method names,
and do not truncate test code by telling it to include all
closing braces explicitly.

C. TEST REFINEMENT USING GPT-4O
To enhance the original test suite, GPT-4o is called upon
to insert edge cases, refine input diversity, and correct
logical test defects. It was introduced in the refinement
phase due to its strong contextual understanding of both
code and accompanying test logic, rich semantic reasoning,
and high accuracy in identifying edge cases and assertion
depth. Rather than starting with GPT, which could risk
over-engineering test cases or emphasizing correctness pre-
maturely (before broad coverage was attempted), we chose
to invoke GPT-4o only after a structured base was built by
Gemini. This made it possible for GPT to concentrate only
on refinement—improving correctness, input diversity, and
coverage—rather than structural generation. Both the original
class and the derived test class are included in the GPT-
4o prompt, along with an extensive collection of refinement
commands. The main changes that are being asked for
are
• Add tests for corner and boundary cases (such as null
values, zero, and max/min bounds).
• Increase the depth of the assertion by verifying more
precise return values and post-conditions.
• To maintain encapsulation boundaries, avoid creating
test cases for private methods.
• Test methods should be properly named and mapped to
the methods that are being tested.
• To expand the scope of test coverage, incorporate
realistic input variations.
• Make sure the test suite compiles and executes properly
to confirm accuracy.
GPT-4o refines the test cases with a variety of inputs and
assertions, as explained in Algorithm 3.

they are written. Any test failures, including compilation

automatically identified and recorded during this phase. The

1) JACOCO FOR COVERAGE MEASUREMENT
The Java code coverage library is called JaCoCo. It explains
the amount of source code that runs when testing an
application and provides information about the completeness
of test cases generated. JaCoCo verifies line coverage
by verifying how many lines of code have been run
during testing. It also verifies branch coverage to make
sure that conditional paths have been tested (if/else/switch
statements). It verifies instruction coverage via executed
bytecode instructions and inspected complexity, quantified as
cyclomatic complexity, which is the number of independent
paths within the program. It offers detailed statistics on line
coverage (the rate of lines covered by tests) and branch
coverage (the rate of decision points tested). The integration is
generally managed using Maven or Gradle plugins, which are
set to gather coverage information during the test phase of the
build lifecycle. When run, JaCoCo generates comprehensive
reports in HTML and XML formats. These reports are
automatically processed to identify if 100% line and branch
coverage goals are achieved. When gaps in coverage are
identified, the related methods or branches are indicated, and
the steps of prompt generation or test refinement are redone
accordingly.By enabling data-driven enhancement of test
prompts and guiding LLMs toward producing more thorough
and accurate test suites, the feedback loop transforms JaCoCo
into a validation checkpoint of significance.

F. WHY GEMINI COMBINED WITH GPT-4O PRODUCES
BETTER RESUL TS
We hypothesize that the combined Gemini + GPT-4o pipeline
benefits from a division of responsibilities. Gemini, guided
by structural metadata, may be more effective at generating
organized and syntactically correct test skeletons aligned
with method signatures and control structures. Applying
GPT-4o later could improve the tests’ semantic quality by
enhancing input diversity, exception handling, and edge
case coverage. Together, this ‘‘coarse-to-fine’’ cascade may
allow Gemini to construct the initial skeleton while GPT-
4o refines it, potentially identifying missing assertions,
improving input-output mappings, and strengthening post-
condition validation.
While Gemini alone produces the lowest test failure rate
(9.78%), the combined Gemini + GPT-4o approach achieves
significantly higher coverage across instruction (93.91%),
branch (99.05%), line (90.48%), and complexity (82.52%).
The slight increase in failure rate (12.14%) reflects the
generation of more challenging and diverse test cases, which
in turn improves the ability to expose hidden bugs and
exercise under-tested code paths. Thus, when balancing
breadth of coverage and defect detection potential, multi-
LLM chaining represents the more effective approach, even
if single LLMs achieve marginally lower failure rates.
G. THREATS TO VALIDITY
In this subsection, we state possible risks that could com-
promise the dependability, applicability, and explainability
of our multi-LLM chaining technique. Apart from prompt
sensitivity and dataset constraints, other LLM uncertainty,
code complexity, and computation overhead-related consid-
erations are discussed.
The initial threat is the overreliance on prompt engineering
and deterministic chaining logic employed in orchestrat-
ing cross-interaction among multiple LLMs. Although the
chaining approach starting with Gemini for test generation
and improvement by GPT-4o provided better outcomes, the
influence of prompt wording and order on quality of output
is still a risk. Small prompt variations or task order deviations
can impact the reproducibility and reliability of test cases.
A second threat arises due to the unpredictability and
stochastic nature of LLMs. We note that even at low
temperature, the same prompt may give slightly different
outputs at different runs, and such variation may cascade into
the chained process. Randomness cannot be completely elim-
inated, although several independent runs were performed to
mitigate the effect of randomness on the output.
Another threat is in the use of the HumanEval dataset
for benchmarking purposes. While it offers standardized
functions appropriate for test generation, it is primarily made
up of algorithmic problems that neither capture fully the
diversity nor the complexity of commercial software projects.
Larger classes, with more complex control flow, state, and
dependencies are also likely to reduce the effectiveness
of our approach, especially when prompt truncation or
context-window limits are encountered.
Another possible threat relates to the measure of code
coverage as a metric. We measured code coverage with the
tool JaCoCo, which tracks both line coverage and branch
coverage. However, high coverage does not equate to good
testing and bug detection. Without the use of fault injection or
mutation testing, we do not know if the functional adequacy
of the tests that were generated.
Another practical limitation is that a multi-LLM workflow
can be computationally expensive. Chaining Gemini, GPT-4o
adds additional latency and API usage costs. This overhead
is fine for controlled experiments, but may prove too large
for integration into real CI/CD pipelines, unless caching or
incremental regeneration approaches are implemented.
Lastly, the application of LLMs was somewhat com-
plicated. While chaining and merging reduced redundancy
while improving coverage, there is a risk of overfitting
to certain evaluation metrics (e.g., coverage %) instead of
real behavioral correctness. In addition, manual merging of
LLMs, to my knowledge, might not be generalizable or
scalable across situations.

• Internal Validity: Potential sources of bias are intro-

• Construct Validity: Generated test evaluation was

we notice are not due to random chance. Although
LLM chaining performance was better than single-LLM
configurations uniformly, a replication study using other
datasets and models is needed to confirm the stability of

V. CONCLUSION AND FUTURE WORK
This paper shows how the automation of test case generation
for Java programs can be greatly improved by integrating
several large language models (LLMs) in a structured
pipeline. In our approach, coverage is the primary measure
of test quality, as it remains the most comprehensive standard
within software testing research and practice. To highlight
the strength of proposed work, we also integrated error
detection methods such as mutation testing, which evaluates
whether the generated test suites can effectively detect and
eliminate the injected faults or not, which provided the greater
insight into test robustness and effectiveness. Our finding
suggests that Gemini + GPT-4o is the top-performing model
which obtained better results in both coverage measures and
mutation testing. So, it confirms the reliability of Gemini +
GPT-4o in real-world applications. These results verified the
industrial relevance of LLM chaining to enhance software
testing practice and future industrial deployment potential.

The JaCoCo usage for coverage measurement and JUnit

models, enabling enhanced efficiency and dependability as

APIs can result in noticeable computation overhead because

efficiency. In real-world deployments, organizations should
consider batch requests, cache intermediate results, or trigger
the pipeline at a granularity only involving changed modules,
in order to keep both latency and cost manageable. Further
research will examine dynamic LLM selection methods in
terms of source code complexity, and adaptive prompt tuning
methods based on past performance and ongoing feedback.

test generation a flexible, usable part of modern software
engineering.

adopting AI in software testing by addressing real industry
